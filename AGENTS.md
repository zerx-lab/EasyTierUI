# AGENTS.md

EasyTierUI is a client for [EasyTier](https://github.com/EasyTier/EasyTier), a decentralized mesh VPN, on the desktops
(macOS, Windows, Linux), mobile (iOS, Android) and the web. It is one Rust app on Native Shell (NSH 0.3: `nsh-core` for
primitives, layout and reactivity, `nsh-base` for unstyled behavior components and the theme), rendered with each
platform's own UI. Its job: deploy, configure and run EasyTier networks quickly, correctly and safely — an individual
joins or creates a network in a minute with safe defaults; an administrator manages many nodes and networks through
easytier-web; anyone can host or deploy that control plane.

Every platform gets the same UI and every feature, organized as switchable **roles** that combine: **node** (this
device in the mesh, `easytier-core`), **console** (managing an easytier-web server), **control-plane host** (running
`easytier-web`). On a Linux server the product is headless EasyTier processes plus EasyTierUI's web build as the
dashboard. Where a platform physically cannot do something (a browser cannot be a node, a phone cannot host a server),
the same page acts on a remote target and says so ("Roles and the core boundary").

The EasyTier programs are external, replaceable components that the user upgrades independently of the UI. Product
truth is in `PRODUCT.md`, the visual system in `DESIGN.md` (its tokens in `theme.json`), topic rules in `.omp/rules/`
(read them as `rule://<name>`). This file is the short version and the authority.

## Layout

```
nsh.json              NSH manifest: "rust": "." (this crate), "root": "App", "theme": "theme.json", "appearance": "system"
theme.json            Design tokens (shadcn cssVars, light + dark) that DESIGN.md specifies; the only file with raw colors
Cargo.toml            The app crate `nsh-app-easytierui` and its lint table: panic-free, `forbid(unsafe_code)`
clippy.toml           Lint configuration: test code may panic; char-boundary `String`/`str` methods and `process::abort` disallowed
rust-toolchain.toml   Stable Rust with rustfmt, clippy and the iOS / Android / web targets
.rustfmt.toml         Formatting (nightly options: `cargo +nightly fmt --all`)
src/lib.rs            The UI set (`#[native_module("easytierui/native")]`) and the root component `App`
src/main.rs           `cargo run`: the root, with theme.json, on this machine's desktop backend
App.test.tsx          The root tested from TypeScript, headless (`nsh test`)
PRODUCT.md            Users, purpose, constraints, open decisions (impeccable product record)
DESIGN.md             Design system: tokens, named rules, components; `.impeccable/design.json` is its sidecar
.omp/                 Agent configuration: RULES.md, rules/ (TTSR + rulebook), commands/verify.md, hooks/pre/guard.ts, lsp.json
.nsh/                 Generated by nsh (types, runners, packages): never edited, never committed
```

Where new code goes — create each module when its first real code lands, not before:

```
src/core/             Roles and the core boundary: domain types (NetworkProfile, NetworkState, PeerSummary, CoreVersion,
                      Target, Role, ...), the backend traits, capability queries per platform
  sidecar/            Desktops, node role: runs and supervises the official easytier-core binary, installs / verifies /
                      switches release versions, reads state through easytier-cli -o json on the loopback RPC portal
  controlplane/       Desktops, host role: runs the official easytier-web binary of the same release, first-run hardening,
                      administered through its REST API on loopback
  embedded/           iOS / Android, node role: EasyTier's library behind the same trait (a platform constraint; needs an
                      FFI crate and the user's approval)
  remote/             Console role on every platform: easytier-web REST client (same origin in the web build)
src/deploy/           Server deployment artifacts: Docker Compose / systemd / reverse proxy, rendered from typed templates
src/profile/          Network profiles: model, validation, TOML rendering, import / export, secret storage
src/store.rs          App state: signals behind functions; pages read signals and call functions; per-target state
src/shell/            The root's layout: the custom desktop title bar, sidebar (wide) or NavStack (compact), target switcher
src/pages/            One module per page (`NavPage`); the same pages on every platform
src/components/       The app's styled components, built on nsh-base and theme tokens
src/i18n/             Every user-facing string, zh-CN and en
tests/<name>/main.rs  Integration tests: one test binary, a module per area; captured core / web output as fixtures
```

Dependency direction: shell → pages → store → `core` / `profile` / `deploy`; components depend on `nsh-base` / `nsh-core`
only; `core` never depends on UI code. Nothing outside `src/core/` and `src/deploy/` names an EasyTier crate, binary,
flag, RPC method or JSON field; pages ask `core` what the current platform and target can do, never `cfg!` on their own.

## Commands

```sh
nsh run                                     # this machine's backend; --target ios|android|web|macos|linux|windows
nsh check                                   # cargo check of the crate, then type checks App.test.tsx
nsh test                                    # cargo test, then App.test.tsx headless; --target <platform> on a real one
nsh test nsh.json --trace                   # headless: what the root mounts and the time of each commit
nsh package --target web                    # or ios, android, macos, linux, windows
cargo run                                   # the root directly on the desktop backend
cargo +nightly fmt --all                    # .rustfmt.toml uses nightly options
cargo clippy --all-targets -- -D warnings   # the lint table; must be clean
cargo test
omp ttsr scan                               # which .omp/rules match the tree (after changing rules)
easytier-core --check-config -c <file>      # validate a rendered config without starting a network
easytier-cli -p 127.0.0.1:<port> -o json node   # what the sidecar backend reads (peer, route, connector, stats, ...)
easytier-web --db <tmp>/et.db --api-server-addr 127.0.0.1   # a throwaway local control plane (seeds admin/admin, user/user)
```

`.omp/commands/verify.md` (`/verify`) runs the checks in order.

## Rules

### Roles and the core boundary (the architecture rules)

- **One client, every platform, every feature** (the user's decision): the same pages everywhere, organized by role —
  node, console, control-plane host — and by target (this device, a console server, the hosted control plane). Roles
  combine; switching role or target never loses another role's state. Platform limits are capabilities `core`
  reports, and the page shows the remote alternative instead of hiding the feature:

  | | Node | Console | Control-plane host |
  |---|---|---|---|
  | Desktops | `sidecar` (easytier-core) | `remote` | `controlplane` (easytier-web), opt-in |
  | Android / iOS | `embedded` (iOS: no TUN upstream, open decision) | `remote` | a remote host via console, plus `deploy` artifacts |
  | Web (on the server) | the server's own core, managed through the co-located easytier-web | `remote`, same origin | it is that easytier-web's dashboard; process settings via `deploy` |

- **Node config source** per instance: *local* (a profile edited here) or *managed* (`--config-server` +
  persisted `--machine-id`, configs pushed by a control plane); managed instances are read-only locally.
- **The EasyTier programs are upgraded freely, independently of the UI** (the user's decision). The desktops run the
  official release binaries (`easytier-core`, `easytier-web`, from one release) as separate processes and never link
  EasyTier's crates. Contracts, most stable first: the TOML config file, process flags, `easytier-cli -o json` of the
  same release, easytier-web's REST API, the RPC portal.
- **Mobile is the exception the platform forces**: iOS cannot spawn processes, Android hands the VpnService TUN fd to
  in-process Rust. `src/core/embedded/` links EasyTier's library from git, pinned to one rev for `easytier`,
  `easytier-core` and `easytier-proto` (crates.io's `easytier` is stale at 2.0.3), target-gated, upgraded with app
  releases, reviewed for LGPL-3.0. Adding it, and the FFI crate it needs, is the user's decision.
- **Servers** run headless: easytier-web (and a core when the server is also a node or relay), with EasyTierUI's web
  build (`nsh package --target web`) as the dashboard on the same origin as the REST API behind an HTTPS reverse proxy.
  `src/deploy/` renders the Docker Compose (official `easytier/easytier` image pinned by digest) or systemd artifacts.
- UI code uses the app's domain types only; a renamed EasyTier field is fixed in one adapter.
- **Versions**: detect with `--version` of each program (and the server's for `remote`), gate features on the detected
  version, keep `MIN_CORE_VERSION` in one place; unsupported or missing programs are a clear UI state with a way out.
  Parse output tolerantly (`#[serde(default)]`, no `deny_unknown_fields`, `#[serde(other)]`).
- **Upgrades**: from EasyTier's GitHub releases over HTTPS; verify the asset's sha256 `digest` from the release API
  before unpacking; install side by side under the app's data directory (`cores/<version>/`), keep the previous version
  for rollback; never install silently; a user-chosen binary needs explicit confirmation.

### Security

- **Secrets** (network secret, easytier-web passwords, session cookie and its own internal / webhook / OIDC secrets,
  private keys, credential and group secrets, config-server URL) live in a redacting `Secret` newtype and the OS
  keychain; never in logs, user-facing errors, argv (`--network-secret` and friends are forbidden), derived `Debug`,
  fixtures or commits, and in the environment only where an easytier-web version reads that secret from its own
  variable (set on that one child). Config files that must hold them are written atomically with owner-only
  permissions in the app's data directory.
- **RPC portal**: always `--rpc-portal 127.0.0.1:<port>` (a bare port binds every interface) with
  `--rpc-portal-whitelist 127.0.0.1/32,::1/128`. It has no authentication; never expose or widen it.
- **Launching**: spawn binaries directly with an argument vector, never through a shell; validate with
  `--check-config` first; pass `--disable-env-parsing` so configs never expand environment variables.
- **Privileges**: the UI never runs elevated. Only the core gets root / Administrator / `CAP_NET_ADMIN` for TUN, through
  the OS's mechanism, after the user agrees; `no_tun` needs none.
- **Safe defaults**: encryption on (`aes-gcm`; `xor` is never called encryption); CSPRNG network secrets of at least
  128 bits and a warning on weak typed ones (EasyTier's digest is SipHash, not a KDF); exit node, subnet proxy, port
  forwarding, SOCKS5, listeners on all interfaces and relay settings off until the user turns them on, with an
  explanation; no hard-coded public shared nodes; easytier-web over HTTPS / WSS except loopback; no telemetry.
- **Hosting / deploying easytier-web**: a fresh database has `admin` / `admin` and `user` / `user`, so both passwords
  are replaced before the REST API is reachable beyond loopback; `--api-server-addr 127.0.0.1` behind an HTTPS proxy;
  `--disable-registration` once the owner exists; `--allow-auto-create-user` off; database and logs owner-only; its own
  secrets never on the command line; the config-server URL's account name is an enrollment credential.
- **Imports** (TOML, links, QR codes) are untrusted: validate every field and show what will change before applying;
  never auto-start an imported profile.

### Correctness

- A network's state is what the core reports: `Stopped`, `Starting`, `Running(snapshot)`, `Stopping`,
  `Failed { reason }`; never "connected" before the core says so, and a peer list shows when it was read.
- Profiles render to TOML through a serializer from typed structs and round-trip; every rendered shape has a test.
- Peer and listener URLs are parsed (`url::Url`), schemes and default ports from one table
  (`rule://easytier-config-security`); encryption settings must match peers, and the UI says so.
- Work against the core runs off the main thread; results carry the revision they answer and stale ones are dropped;
  a crashed core is a UI state with a restart, never a UI crash.

### UI

- `DESIGN.md` is the visual authority: colors from `theme.json` tokens via `theme()` (no raw colors, `rule://ui-theme-tokens`),
  the spacing / type / radius scale (no literal points, `rule://ui-scale-literals`), light and dark, both first-class.
- Native chrome: the system header, back gesture and alerts on iOS / Android, a sidebar shell on the desktops under
  the app's own title bar (the system's hidden with `set_title_bar(TitleBarStyle::Hidden, …)`; the native window
  controls stay where `title_bar()` reports them); touch targets at least 44 × 44 pt; honor `reduce_motion()` and the
  user's text size.
- Every state is designed: empty, loading, error, offline, no privileges, program missing / unsupported / upgrading,
  not available on this platform (with the remote alternative), managed by a control plane (read-only).
- Every string comes from `src/i18n/` in zh-CN and en; EasyTier's terms are used consistently.

### Rust safety (non-negotiable)

- **No panic paths outside tests**, enforced three ways: `Cargo.toml` `[lints]` (`unwrap_used`, `expect_used`, `panic`,
  `unreachable`, `todo`, `unimplemented`, `dbg_macro`, `indexing_slicing`, `string_slice`, `arithmetic_side_effects`,
  `exit`, `print_*`, dropped results, unexplained `allow`s), `clippy.toml` (test exemptions, char-boundary methods,
  `process::abort`), and the TTSR rules in `.omp/rules/` that stop the same constructs while they are written
  (`assert!` / `debug_assert!` too, which clippy cannot deny). How to fail instead: `rule://rust-error-handling`.
- **No `unsafe`**: `unsafe_code = "forbid"`. NSH does the FFI. NSH's `#[class]` expands to `unsafe impl` and so is not
  used here; any bridge that needs `unsafe` (JNI, a Network Extension, EasyTier's C ABI) is a separate crate created by
  user decision, with `// SAFETY:` on every block, while this crate keeps `forbid`.
- The lint policy is never loosened to make a check pass. In tests, `#[test]` functions and `#[cfg(test)]` modules may
  panic; helpers there still avoid unchecked arithmetic and string slicing or carry a scoped `#[expect(…, reason = …)]`.

## Code conventions

- Everything in code is English: identifiers, comments, logs, docs. Comments explain why, not what the code says.
- Log through the `log` facade only (`src/main.rs` installs `env_logger`); never print; never log secrets.
- Errors: a `thiserror` enum per module, variants the UI can act on; no `anyhow` in app code.
- Units and colors are NSH's types: lengths through the scale methods or `Points`, colors `Hsla` from `theme()`.
- State follows NSH's Coding Guides: components run once, signals are read where they are used, stable domain keys for
  lists, `List` for long collections, async work started from events / effects / resources under an owner.
- Dependencies: few and maintained, each justified; EasyTier crates only per "Roles and the core boundary".
- Formatting: `cargo +nightly fmt --all`.

## Commits

- Subjects are `<area>: <What the change does>`: one lower-case area (`core`, `sidecar`, `controlplane`,
  `embedded`, `remote`, `deploy`, `profile`, `store`, `ui`, `pages`, `components`, `theme`, `i18n`, `build`, `docs`,
  `agents`), then an imperative sentence starting with a capital letter, no trailing period, about 72 characters. No
  conventional prefixes (`fix:`, `feat:`).
- The body explains why. One commit does one thing; no unrelated refactors or formatting.
- Never bypass hooks (`--no-verify`); never `push --force` without `--force-with-lease`.

## Parallel agents

Subagents never run `cargo build`, `cargo test`, `cargo clippy`, `cargo run`, `nsh run`, `nsh test`, `nsh package` or
`nsh build` (several at once overload the machine; `.omp/hooks/pre/guard.ts` blocks them); at most `cargo check`. They
write the code and its tests and report which checks to run; the main session runs them one at a time.

No agent elevates privileges, installs or controls system services, changes routes, interfaces or the firewall, or
brings up a real TUN on the user's machine (the guard asks the user first, and blocks subagents). Exercise the core with
`--no-tun` on loopback and easytier-web with `--api-server-addr 127.0.0.1` and a temporary `--db`. Deployment artifacts
are generated and shown; no agent applies them to a real server.

## Verification after changes

1. `cargo +nightly fmt --all`; `cargo clippy --all-targets -- -D warnings` clean; `cargo test`.
2. `nsh check` and `nsh test` (headless).
3. Role / boundary / profile / deployment changes: tests with captured output of a real release (redacted), and when
   release binaries are available, a `--no-tun` core on loopback read back with `easytier-cli -o json`, or a loopback
   easytier-web on a temporary `--db` driven through its REST API; rendered deployment artifacts checked by tests;
   say which version ran.
4. Capability states: each page's behavior on a platform that cannot do its feature locally (web, iOS, Android) has a
   headless test.
5. `.omp/rules/` changes: `omp ttsr test` cases for each new condition and `omp ttsr scan`.
6. UI: looking at the screens (`nsh run`, `nsh test --target <platform>` with screenshots) only when the user asks;
   otherwise report what to check — both appearances, a large text size, a phone, a desktop window and the web build.

Report what ran, its result, and what could not run on this host.
