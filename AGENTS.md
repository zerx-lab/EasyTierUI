# AGENTS.md

EasyTierUI is a client for [EasyTier](https://github.com/EasyTier/EasyTier), a decentralized mesh VPN, on the desktops
(macOS, Windows, Linux), mobile (iOS, Android) and the web. It is one Rust app on Native Shell (NSH 0.3: `nsh-core` for
primitives, layout and reactivity, `nsh-base` for unstyled behavior components and the theme), rendered with each
platform's own UI. Its job: deploy, configure and run EasyTier networks quickly, correctly and safely — an individual
joins or creates a network in a minute with safe defaults; an administrator manages many nodes and networks through
easytier-web; anyone can host or deploy that control plane.

Every platform gets the same UI and every feature, organized as switchable **roles** that combine: **node** (this
device in the mesh, `easytier-core`), **console** (managing an easytier-web server), **control-plane host** (running
`easytier-web`). On a Linux server the product is headless EasyTier processes plus EasyTierUI's web build as the
dashboard. Where a platform physically cannot do something (a browser cannot be a node, a phone cannot host a server),
the same page acts on a remote target and says so ("Roles and the core boundary").

The EasyTier programs are external, replaceable components that the user upgrades independently of the UI. Product
truth is in `PRODUCT.md`, the visual system in `DESIGN.md` (its tokens in `theme.json`), topic rules in `.omp/rules/`
(read them as `rule://<name>`). This file is the short version and the authority.

## Layout

```
nsh.json              NSH manifest: "rust": "." (this crate), "root": "App", "theme": "theme.json", "appearance": "system", "icon"
theme.json            Design tokens (shadcn cssVars, light + dark) that DESIGN.md specifies; the only file with raw colors besides brand/

Cargo.toml            The app crate `nsh-app-easytierui` and its lint table: panic-free, `forbid(unsafe_code)`

rust-toolchain.toml   Stable Rust with rustfmt, clippy and the iOS / Android / web targets
.rustfmt.toml         Formatting (nightly options: `cargo +nightly fmt --all`)
src/lib.rs            The UI set (`#[native_module("easytierui/native")]`) and the root component `App`
src/main.rs           `cargo run`: the root, with theme.json, on this machine's desktop backend

DESIGN.md             Design system: tokens, named rules, components; `.impeccable/design.json` is its sidecar
.omp/                 Agent configuration: RULES.md, rules/ (TTSR + rulebook), commands/verify.md, hooks/pre/guard.ts, lsp.json
.nsh/                 Generated by nsh (types, runners, packages): never edited, never committed
```

The source tree (each module was created when its first real code landed):

```
src/core/             Roles and the core boundary: domain types (Secret, CoreVersion, NetworkState, NodeSnapshot,
                      PeerSummary, Target, Role, ...), the NodeBackend / ProgramSource traits, capabilities per platform,
                      the data directory (owner-only files), the keychain (SecretStore), net (peer / listener URLs),
                      settings (the core's switches, port forwards, VPN portal, mapped listeners), acl (ACL v1 chains,
                      rules and groups, group secrets apart) shared by local profiles and console configs, and desktop
                      (the app's own tray, single instance and login item, through `crates/desktop-shell`)
  sidecar/            Desktops, node role: the official easytier-core as the app's child (no TUN) or as an OS service
                      `easytierui-<key>` installed through `easytier-cli service` after the user agrees (TUN); state
                      through easytier-cli -o json on the loopback RPC portal
  install/            Desktops: EasyTier releases from GitHub, sha256-verified, side by side under `cores/<version>/`,
                      active / previous pointers (switch, roll back), a user-chosen directory after confirmation
  controlplane/       Desktops, host role: the official easytier-web of the active release, first-run hardening,
                      administered on loopback
  embedded/           iOS / Android, node role: EasyTier's library in process through `crates/easytier-mobile`
  remote/             Console role on every platform: easytier-web REST client over NSH `fetch` (same origin on the web)
crates/easytier-mobile/  The UniFFI bridge: the only crate that links EasyTier's library (git, pinned to v2.6.4), mobile
                      targets only; its README holds the LGPL-3.0 note and the binding generation steps
crates/desktop-shell/ Desktops: the tray icon (show / quit), closing to the tray, starting hidden, one instance per
                      user, the login item (LaunchAgent / HKCU Run / XDG autostart); NSH 0.3 has no API for them.
                      `unsafe` only in macos.rs / windows.rs (the user's decision)
src/deploy/           Server deployment artifacts: Docker Compose / systemd / reverse proxy / firewall / README, rendered
                      from a validated DeploymentPlan
src/profile/          Network profiles: model, validation, TOML rendering, import / share links / QR, persistence
src/store/            App state: the root Store (targets, pages, language, work mode), one sub-store per role (node,
                      console, host, versions) and desktop (tray, quiet start, login item); pages read signals and call
                      functions; per-target state
src/shell/            The root's layout: the custom desktop title bar, sidebar (wide) or NavStack (compact), target switcher
src/pages/            One module per role (node/, console/, host/) and settings.rs; the same pages on every platform;
                      config/ holds the editor parts both network editors share (feature switches, the ACL editor)
src/components/       The app's styled components, built on nsh-base and theme tokens
src/i18n/             Every user-facing string, zh-CN and en: root strings plus one struct per area (common, node, console,
                      host, versions, desktop, config: the shared network-editor parts)
tests/app/            Integration tests: one test binary, a module per area, headless on NSH's engine
tests/fixtures/       Captured, redacted output of a real release (easytier-2.6.4/), GitHub releases, deployment snapshots
```

Dependency direction: shell → pages → store → `core` / `profile` / `deploy`; components depend on `nsh-base` / `nsh-core`
only; `core` never depends on UI code. Nothing outside `src/core/`, `src/deploy/` and `crates/easytier-mobile/` names an
EasyTier crate, binary, flag, RPC method or JSON field; pages ask `core` what the current platform and target can do,
never `cfg!` on their own (the store picks a backend by compile target).

## Rules

### Roles and the core boundary (the architecture rules)

- **One client, every platform, every feature** (the user's decision): the same pages everywhere, organized by role —
  node, console, control-plane host — and by target (this device, a console server, the hosted control plane). Roles
  combine; switching role or target never loses another role's state. Platform limits are capabilities `core`
  reports, and the page shows the remote alternative instead of hiding the feature. Which roles the shell lists is the
  user's **work mode** (the user's decision, `core::role::WorkMode`, storage key `ui.mode`): asked once on the first
  run of a desktop or phone — *client* (node only, preselected) or *control* (every role) — and changed in Settings,
  which adds *custom* (a switch per role, one always on); the web build is a control plane's dashboard and never
  asks. Hiding a role stops and forgets nothing, and a hidden role that still runs something here (this device's
  networks, the hosted easytier-web) keeps a sidebar row to its pages:

  | | Node | Console | Control-plane host |
  |---|---|---|---|
  | Desktops | `sidecar` (easytier-core) | `remote` | `controlplane` (easytier-web), opt-in |
  | Android / iOS | `embedded`, no TUN in this build (see below) | `remote` | a remote host via console, plus `deploy` artifacts |
  | Web (on the server) | a machine enrolled in the serving easytier-web, picked on the page and managed through its REST API | `remote`, same origin, every `proxy-rpc` service 2.6.4 answers | it is that easytier-web's dashboard: status and the hardening it can do through REST (the signed-in account's password); process settings via `deploy` |

- **Node config source** per instance: *local* (a profile edited here) or *managed* (`--config-server` +
  persisted `--machine-id`, configs pushed by a control plane); managed instances are read-only locally, run as the
  user's child process without TUN, and get the config-server URL only through `ET_CONFIG_SERVER` on that one child.
- **The EasyTier programs are upgraded freely, independently of the UI** (the user's decision). The desktops run the
  official release binaries (`easytier-core`, `easytier-web`, from one release) as separate processes and never link
  EasyTier's crates. Contracts, most stable first: the TOML config file, process flags, `easytier-cli -o json` of the
  same release, easytier-web's REST API, the RPC portal.
- **TUN on the desktops runs as an OS service** (the user's decision): a TUN profile is installed as the service
  `easytierui-<key>` through `easytier-cli service install` of the active release, after a confirmation that explains
  the administrator prompt and that the network keeps running after the app quits; install, start, stop and uninstall
  each go through the OS's elevation (Linux `pkexec`; macOS `osascript` with `quoted form of` argv; Windows PowerShell
  `Start-Process -Verb RunAs`). The service never runs files the user can write: the elevated program is the app's own
  executable re-run with a typed request (`--etui-privileged`; no shell, values only as arguments), which copies
  `easytier-core`, `easytier-cli` and the rendered config into an administrator-only directory (macOS
  `/Library/Application Support/EasyTierUI/services/<key>/`, Linux `/var/lib/easytierui/<key>/`, Windows
  `%ProgramData%\EasyTierUI\<key>\` with an Administrators / SYSTEM ACL), checks the copies' sha256 against the digests
  taken just before the prompt, and runs the copied CLI; every service argument points at the copies, later
  `start` / `stop` / `uninstall` run the copied CLI, and uninstall deletes the directory. Autostart at boot is off
  (`--disable-autostart true`). `no_tun` profiles run as the app's child process and stop with it.
- **Mobile is the exception the platform forces**: iOS cannot spawn processes, Android hands the VpnService TUN fd to
  in-process Rust. `crates/easytier-mobile` (UniFFI, the user's decision) links EasyTier's library from git pinned to
  v2.6.4 (`8428a89d`), mobile targets only, upgraded with app releases; `src/core/embedded/` drives it through its Rust
  API. NSH 0.3's packaging cannot add an Android VpnService or an iOS Network Extension, so in-app nodes run `no_tun`
  until a host app hands a TUN fd to `set_tun_fd`. The LGPL-3.0 review of shipping it statically linked is open.
- **Servers** run headless: easytier-web (and a core when the server is also a node or relay), with EasyTierUI's web
  build (`nsh package --target web`) as the dashboard on the same origin as the REST API behind an HTTPS reverse proxy.
  `src/deploy/` renders the Docker Compose (official `easytier/easytier` image pinned by digest) or systemd artifacts.
- UI code uses the app's domain types only; a renamed EasyTier field is fixed in one adapter.
- **Versions**: detect with `--version` of each program (and the server's for `remote`), gate features on the detected
  version, keep `MIN_CORE_VERSION` in one place; unsupported or missing programs are a clear UI state with a way out.
  Parse output tolerantly (`#[serde(default)]`, no `deny_unknown_fields`, `#[serde(other)]`).
- **Upgrades**: from EasyTier's GitHub releases over HTTPS; verify the asset's sha256 `digest` from the release API
  before unpacking; install side by side under the app's data directory (`cores/<version>/`), keep the previous version
  for rollback; never install silently; a user-chosen binary needs explicit confirmation.

### Desktop shell (the app's own window behavior)

- **Keep to the tray** (on by default), **start at login** and **start quietly** (the user's decisions) are Settings →
  Desktop; phones and the web show that they belong to the desktop app. Closing the window hides it only while a tray
  icon exists to bring it back: a tray that cannot be made, or a Linux desktop without a StatusNotifierWatcher host,
  leaves closing to quit, and the switch says why. Quiet start hides the window at every launch and needs the tray.
  On macOS a window hidden to the tray takes the app out of the Dock (accessory activation policy) until it shows
  again; without a tray icon the app stays in the Dock, whose icon reopens the window.
- **One instance per user**: the first holds `instance.lock` in the data directory and listens on a loopback port that
  only understands "show the window"; a later launch asks it to show and quits before its Store starts, so the same
  networks never run twice. Headless runs (no NSH window) skip it.
- **Login item**: per user, never a system service and never elevated — `~/Library/LaunchAgents/<id>.login.plist`,
  `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, `$XDG_CONFIG_HOME/autostart/<id>.desktop` — pointing at the
  current executable (rewritten at start while on). Tests use the in-memory one (`test.login-item=memory`).
- `crates/desktop-shell` attaches to NSH's window: a stand-in AppKit window delegate forwarding to NSH's (macOS), a
  Win32 subclass of the `NshWindow` (Windows), GTK's `close-request` and a replaced `app.quit` (Linux); tray-icon with
  its `ksni` backend on Linux (GTK 3 cannot share a process with NSH's GTK 4). NSH runs the app on its engine thread,
  not the window's: the crate's API works from any thread and posts every window and tray step to the UI thread (the
  main dispatch queue; a `WH_GETMESSAGE` hook on NSH's `nsh-ui` thread; GLib's default main context). Only
  `src/core/desktop.rs` names it.

### Security

- **Secrets** (network secret, easytier-web passwords, session cookie and its own internal / webhook / OIDC secrets,
  private keys, credential and group secrets, config-server URL) live in a redacting `Secret` newtype and the OS
  keychain; never in logs, user-facing errors, argv (`--network-secret` and friends are forbidden), derived `Debug`,
  fixtures or commits, and in the environment only where the program reads that secret from its own variable, set on
  that one child (`ET_CONFIG_SERVER` for a managed core, `OIDC_CLIENT_SECRET` for easytier-web). Config files that
  must hold them are written atomically with owner-only permissions in the app's data directory. The core prints its
  whole config, secret included, at startup: every captured log line is redacted before it is kept.
- **RPC portal**: always `--rpc-portal 127.0.0.1:<port>` (a bare port binds every interface) with
  `--rpc-portal-whitelist 127.0.0.1/32,::1/128`. It has no authentication; never expose or widen it.
- **Launching**: spawn binaries directly with an argument vector, never through a shell (the app runs no shell at
  all, elevated or not); validate with `--check-config` first; pass `--disable-env-parsing` so configs
  never expand environment variables; strip inherited `ET_*` variables from every child.
- **Privileges**: the UI never runs elevated. Only the core gets root / Administrator / `CAP_NET_ADMIN` for TUN, as an
  OS service installed through the OS's mechanism after the user agrees; `no_tun` needs none. What the elevated step
  runs is never a file the user can write: the service files are copies in an administrator-only directory, checked
  against digests taken just before the prompt (the elevated process is the app's own executable doing only that
  typed request, no UI).
- **Safe defaults**: encryption on (`aes-gcm`; `xor` is never called encryption); CSPRNG network secrets of at least
  128 bits and a warning on weak typed ones (EasyTier's digest is SipHash, not a KDF); exit node, subnet proxy, port
  forwarding, SOCKS5, the WireGuard VPN portal, kernel forwarding of proxied subnets, listeners on all interfaces and
  relay settings off until the user turns them on, with an explanation; no hard-coded public shared nodes;
  easytier-web over HTTPS / WSS except loopback; no telemetry.
- **Hosting / deploying easytier-web**: a fresh database has `admin` / `admin` and `user` / `user`, so both passwords
  are replaced before the REST API is reachable beyond loopback; `--api-server-addr 127.0.0.1` behind an HTTPS proxy
  (in Docker Compose the container's loopback cannot be tunnelled to, so the API listens on the compose network only
  and is published on the host's `127.0.0.1`); `--disable-registration` from the very first start (a hosted web is
  launched without registration open except for the loopback-only owner-registration window, and its `admin` /
  `user` passwords are replaced before the console is offered); machines enroll under a CSPRNG owner account
  (`owner-<10 base32>`, secrets `host/owner-name` / `host/owner-password`), never `admin` / `user`;
  `--allow-auto-create-user` off; database and logs owner-only; its own secrets never on the command line; the
  config-server URL's account name is an enrollment credential. Deployment artifacts carry one hardening switch:
  until it is flipped the proxy answers `/api/` with 403 and the operator hardens through an SSH tunnel.
- **Imports** (TOML, links, QR codes) are untrusted: validate every field and show what will change before applying;
  never auto-start an imported profile.

### Correctness

- A network's state is what the core reports: `Stopped`, `Starting`, `Running(snapshot)`, `Stopping`,
  `Failed { reason }`; never "connected" before the core says so, and a peer list shows when it was read.
- Profiles render to TOML through a serializer from typed structs and round-trip; every rendered shape has a test.
- Peer and listener URLs are parsed (`url::Url`), schemes and default ports from one table
  (`rule://easytier-config-security`); encryption settings must match peers, and the UI says so.
- Work against the core runs off the main thread; results carry the revision they answer and stale ones are dropped;
  a crashed core is a UI state with a restart, never a UI crash.

### UI

- `DESIGN.md` is the visual authority: colors from `theme.json` tokens via `theme()` (no raw colors, `rule://ui-theme-tokens`),
  the spacing / type / radius scale (no literal points, `rule://ui-scale-literals`), light and dark, both first-class.
- Native chrome: the system header, back gesture and alerts on iOS / Android, a sidebar shell on the desktops under
  the app's own title bar (the system's hidden with `set_title_bar(TitleBarStyle::Hidden, …)`; the native window
  controls stay where `title_bar()` reports them); touch targets at least 44 × 44 pt; honor `reduce_motion()` and the
  user's text size.
- Every state is designed: empty, loading, error, offline, no privileges, program missing / unsupported / upgrading,
  not available on this platform (with the remote alternative), managed by a control plane (read-only).
- Every string comes from `src/i18n/` in zh-CN and en; EasyTier's terms are used consistently.

### Rust safety (non-negotiable)

- **No panic paths outside tests**, enforced three ways: `Cargo.toml` `[lints]` (`unwrap_used`, `expect_used`, `panic`,
  `unreachable`, `todo`, `unimplemented`, `dbg_macro`, `indexing_slicing`, `string_slice`, `arithmetic_side_effects`,
  `exit`, `print_*`, dropped results, unexplained `allow`s), `clippy.toml` (test exemptions, char-boundary methods,
  `process::abort`), and the TTSR rules in `.omp/rules/` that stop the same constructs while they are written
  (`assert!` / `debug_assert!` too, which clippy cannot deny). How to fail instead: `rule://rust-error-handling`.
- **No `unsafe`**: `unsafe_code = "forbid"`. NSH does the FFI. NSH's `#[class]` expands to `unsafe impl` and so is not
  used here; any bridge that needs `unsafe` (JNI, a Network Extension, EasyTier's C ABI) is a separate crate created by
  user decision, with `// SAFETY:` on every block, while this crate keeps `forbid`. The one so far:
  `crates/desktop-shell` (`unsafe_code = "deny"`, lifted by a module-level `expect` in `macos.rs` and `windows.rs`
  only; the TTSR rules `rust-no-unsafe` and `rust-allow-reason` leave exactly those two files out of scope).
- The lint policy is never loosened to make a check pass. In tests, `#[test]` functions and `#[cfg(test)]` modules may
  panic; helpers there still avoid unchecked arithmetic and string slicing or carry a scoped `#[expect(…, reason = …)]`.

## Code conventions

- Everything in code is English: identifiers, comments, logs, docs. Comments explain why, not what the code says.
- Log through the `log` facade only (`src/main.rs` installs `env_logger`); never print; never log secrets.
- Errors: a `thiserror` enum per module, variants the UI can act on; no `anyhow` in app code.
- Units and colors are NSH's types: lengths through the scale methods or `Points`, colors `Hsla` from `theme()`.
- State follows NSH's Coding Guides: components run once, signals are read where they are used, stable domain keys for
  lists, `List` for long collections, async work started from events / effects / resources under an owner.
- Dependencies: few and maintained, each justified; EasyTier crates only per "Roles and the core boundary".
- Formatting: `cargo +nightly fmt --all`.

## Commits

- Subjects are `<area>: <What the change does>`: one lower-case area (`core`, `sidecar`, `controlplane`,
  `embedded`, `remote`, `deploy`, `profile`, `store`, `ui`, `pages`, `components`, `theme`, `i18n`, `build`, `docs`,
  `agents`), then an imperative sentence starting with a capital letter, no trailing period, about 72 characters. No
  conventional prefixes (`fix:`, `feat:`).
- The body explains why. One commit does one thing; no unrelated refactors or formatting.
- Never bypass hooks (`--no-verify`); never `push --force` without `--force-with-lease`.

## Parallel agents

Subagents never run `cargo build`, `cargo test`, `cargo clippy`, `cargo run`, `nsh run`, `nsh test`, `nsh package` or
`nsh build` (several at once overload the machine; `.omp/hooks/pre/guard.ts` blocks them); at most `cargo check`. They
write the code and its tests and report which checks to run; the main session runs them one at a time.

No agent elevates privileges, installs or controls system services, changes routes, interfaces or the firewall, or
brings up a real TUN on the user's machine (the guard asks the user first, and blocks subagents). Exercise the core with
`--no-tun` on loopback and easytier-web with `--api-server-addr 127.0.0.1` and a temporary `--db`. Deployment artifacts
are generated and shown; no agent applies them to a real server.

## Verification after changes

1. `cargo +nightly fmt --all`; `cargo clippy --all-targets -- -D warnings` clean; `cargo test`.
2. `nsh check` and `nsh test` (headless).
3. Role / boundary / profile / deployment changes: tests with captured output of a real release (redacted), and when
   release binaries are available, a `--no-tun` core on loopback read back with `easytier-cli -o json`, or a loopback
   easytier-web on a temporary `--db` driven through its REST API; rendered deployment artifacts checked by tests;
   say which version ran.
4. Capability states: each page's behavior on a platform that cannot do its feature locally (web, iOS, Android) has a
   headless test.
5. `.omp/rules/` changes: `omp ttsr test` cases for each new condition and `omp ttsr scan`.
6. UI: looking at the screens (`nsh run`, `nsh test --target <platform>` with screenshots) only when the user asks;
   otherwise report what to check — both appearances, a large text size, a phone, a desktop window and the web build.
